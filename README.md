# React Native Project Case | Car Rental App

## Project Description

Your task is to design and implement a mobile application in **React Native**. The application is a simple version of a car rental application. Users should be able to view a list of available cars, view the details of each car, and place a booking.

At the beginning of the project, you should use **dummy data** embedded in the application. Later, you will design a simple **backend** to fetch data from.

The requirements for the application's design and implementation are listed below. Feel free to add your own requirements as well, but try to keep the scope limited.

---

## Functional Requirements

1. The user should be able to view a list of cars available.
2. The user should be able to view the details of each available car.
3. The user should be able to place a booking for a car.
4. Use an API to query data.
5. The application should persist the data retrieved from the API.

## Design Requirements

- A separate design document will be uploaded that includes the **5 planes of mobile UX design**:
  1. Strategy
  2. Scope
  3. Structure
  4. Skeleton
  5. Surface

## Implementation Requirements

1. The application must be implemented in React Native.
2. Initially, the application must use dummy data.
3. After lecture 4 (*"Working with API and Persistent Storage"*), a backend application can be added to persist and fetch data.

### AI Policy (shared constant)

**Allowed:** any AI tool in any mode (autocomplete, chat, multimodal, or agentic, e.g. Claude Code, Cursor, GitHub Copilot agent mode, Gemini CLI) for any part of this project, **provided use is disclosed**.

>  **Undisclosed AI use is academic misconduct.** Note the asymmetry: controlled, disclosed AI use that is verified well can earn top marks; hidden use can cost you the course.

#### Four standing rules apply whenever AI touches your project

1. **Disclose in the AI dossier.**
   Continue the log you started in the design document's Appendix A: one entry per significant interaction (tool, mode, task, prompt or link, verification, decision), plus the **failure log**, with at least 3 entries per project documenting AI output that was wrong or off-spec and how you caught it.

2. **AI code enters `main` only through a pull request** that:
   - carries tests,
   - is reviewed by a teammate who did not generate it, and
   - passes CI.

   *"The model wrote it and it ran" is not verification.*

3. **Maintain an agent rules file.**
   Your repository contains a `CLAUDE.md` or `AGENTS.md` describing your conventions, architecture, and definition of done. Evolve it as you learn what your agents get wrong; its git history is evidence of engineering judgment.

4. **You own what you ship.**
   At milestone reviews and the final presentation, any team member may be asked to explain (or live-modify) any line in the repository. Inability to do so caps the individual's grade regardless of team output.
